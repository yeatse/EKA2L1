# S60v5（N97 / RM-507）GUI app 卡在 AVKON FEP / PtiEngine 启动

> 来源：阶段 3「已知风险」（[`../IOS_PORTING_TASKS.md`](../IOS_PORTING_TASKS.md)）。状态：未解决，独立立项。
>
> **一句话结论**：N97 点 Calculator 黑屏 + CPU 100% 是 **backend 无关、iOS 无关**的 EKA2L1 通用 S60v5 重 app 启动缺口；深挖后定论：FEP/Pti 崩溃（`Can't open object: ZIDATA_`）只是稀有副经路，主导黑屏是 dyncom 下 AVKON/CONE/OpenVG/多服务握手的**非确定性卡死**，单解决 FEP 不会让 Calculator 渲染。**实务建议**：N97 用 Zip manager 这类不吃 FEP/OpenVG 的轻量 app 验收；Calculator 等重 app 暂不作为 iOS 验收目标，待 dynarmic-on-sim + S60v5 启动稳定性作为独立大任务推进。

## 初始现象与定性

清掉日志洪水（见阶段 3 修复清单 #5）后，N97 点 Calculator 仍黑屏 + CPU 100%。日志显示 Calculator 线程加载 `PtiKeymappings_507_28.dll` / `PtiZiCore.dll` / `Zi8EnglishUS.dll` 后，`svc OpenObject` 连续报 `Can't open object: ZIDATA_ / ZiAutoCh_`（Zi 引擎按名字打开的全局 RChunk/对象，EKA2L1 未提供），随后 `Access violation reading address 0x10000 in thread Calculator`（dyncom）/ `0x30`（dynarmic 下复现位置不同），Calculator 线程 fault，其它线程空转 → 黑屏 + 100% CPU。这是 **backend 无关、iOS 无关**的 S60v5 输入框架仿真缺口——N95/S60v3 不走这条 Pti/Zi 路径所以能正常渲染。`avkonfep` 补丁本意是 stub 掉 FEP，但 `install_required_rom_patches`（与 Qt/Android 同款）走的是"把 `avkonfep_general.dll` 文件拷到 `Z:\sys\bin\avkonfep.dll`"；**ROM（XIP）设备的 avkonfep 是从 ROM 镜像直接加载的，覆盖 Z 盘文件无效**（对比 goommonitor/scdv 等走 libmanager `.map` patch 机制才真正覆盖了 ROM 里的 DLL）。后续方向：① 给 `src/patch/avkonfep` 补 `.map`，让它走 ROM patch 覆盖、确认能 stub 掉 FEP，从根上绕开 Pti；② 或在内核侧支持 Zi 引擎需要的具名全局对象。

## 深入调查（2026-05-30）

- **不是 iOS 特有问题——桌面 macOS arm64 Qt（dynarmic）跑同一个 N97 ROM 的 Calculator 同样进入 FEP/Pti 路径**（`build/macos/bin/EKA2L1.app --device RM-507 --app 0x10005902`，把 sim sandbox 的 `drives/z/rm-507` + `roms/rm-507` + `devices.yml` 拷到 `~/Library/Application Support/EKA2L1/data` 即可复现）。桌面日志可见 `ecom.dll` → `fepbase.dll` → `ptiengine.dll`(UID3=0x101F8610) → spawn `ecomserver` 扫描 `Z:\private\10009D8F\ecom-*-*.sNN` 注册表。桌面表现为 **CPU ~1% 卡住/等待**（未刷出 UI，无 host 显示无法确认是否渲染），iOS 则继续加载 `PtiZiCore.dll`/`Zi8EnglishUS.dll` 后 `Can't open object: ZIDATA_` → AV → 100% 自旋。即这是 **EKA2L1 通用的 S60v5 输入框架仿真缺口**，不是 iOS 移植引入的。
- **`avkonfep` 补丁对 ROM 设备从未生效的根因**：libmanager 的 patch 机制只对带 `.map` 的 patch 起作用（日志里 `Using general DLL X_general.dll as patch DLL for map file X.dll` 仅出现在 scdv/ecam/mediaclient*/backlightctrl/postingsurfacefactory/audiooutputrouting——这些 `src/patch/*/group/` 下都有 `.dll.map`）。**`src/patch/avkonfep` 只有 `avkonfep_general.dll`、没有 `.map`**，只能靠 `install_required_rom_patches` 的"文件拷到 `Z:\sys\bin\avkonfep.dll`"。而 N97 是 RPKG/ROM 设备：`vfs.cpp` 里 `physical_file_system::mount_volume_from_path` 对 `drive_media::rom` 直接 `return false`，Z 盘走 `rom_file_system`，文件按 SYM.ROM 镜像的 `burn_tree_find_entry` 解析 —— **物理 `drives/z/.../avkonfep.dll` 那个 patch 文件压根不会被加载**（`.bak` 只是 install 时备份了一下，运行期无意义）。FEP 仍由 ECOM 惰性解析到 ROM 里的原生 `avkonfep` → 拉起 Pti。
- **两条修复路径的可行性评估**：① 给 avkonfep 补 `.map` 走 ROM export patch（像 scdv 那样），是"对的方向"，但需要知道 ROM 版 avkonfep 里 FEP 工厂/`ImplementationGroupProxy` 的导出序号去映射、并用 Symbian 工具链重建匹配导出的 `avkonfep_general.dll`，本环境没有该工具链/无法可靠逆出序号；② 在内核侧实现 PtiEngine 需要的具名全局对象（`ZIDATA_`/`ZiAutoCh_`，应是 Zi 引擎进程创建、按名 `RChunk::OpenGlobal` 共享的对象）。两条都属于**跨平台共享内核/ECOM/FEP 的独立上游改动**，回归面大，建议单独立项、在桌面 Qt 上调试（迭代快、可对照），iOS 自动受益。
- **范围界定（2026-05-30）：问题是"会拉起 FEP/Pti 预测输入的 app 特定"，不是 N97/iOS 整体**。同一 iOS N97 ROM 上 **Zip manager（uid=0x2000023D）核心仿真活的**——日志干净（~90 行、无 AV）、窗口服务建出 window 23/24（`Enable alpha`）、CPU 稳定 ~1.6%（空闲等输入），与桌面 N97 行为一致。**（2026-05-30 更正：当时"正常渲染"的判断只基于日志，没看截图；实测 ZipManager 在 iOS 上文字渲染成纯黑块（花屏）、触屏无效——两者均为 iOS 端 bug，已在同日修复，见变更日志。桌面渲染正常。）**即日志洪水修复后 N97 的核心仿真在 iOS 上是活的；只有像 Calculator 这种一上来就吃 AVKON FEP/Pti 预测输入的 app 才会卡在上述 ZIDATA_ 缺口。验收 N97 时优先用 Zip manager 这类不触发 FEP 的 app；Calculator 等待 FEP/Pti 上游修复后再回归。
- **尝试过的修复 & 进一步定位（2026-05-30，均已回退，仅留经验）**：
  1. **试做 ① 的简化版**：新增 `src/patch/avkonfep/group/avkonfep.dll.map`（`[epoc94]/[epoc95]` 段 `1 1`，ECOM 插件 proxy = ordinal 1）+ 从 `install_required_rom_patches` 移除 avkonfep 文件替换。桌面/iOS 实测**无效**：libmanager 确实注册并加载了 patch DLL（`Using general DLL avkonfep_general.dll as patch DLL for map file avkonfep.dll`），但 Calculator 仍拉起 Pti、仍 ZIDATA_ → AV。原因：`does_condition_meet_for_patch` **按 DLL 名字匹配**，而真正运行的 FEP 是 guest `ecomserver` 通过 **ECOM 按实现 UID** 解析、加载成 **UID 命名的插件 DLL**（`Service.Loader:trace` 看到加载 `10281fc6.dll`/`101fe2aa.dll`/`10285d7b.dll` 等，而非名为 `avkonfep.dll` 的模块）——`avkonfep.dll.map` 根本没命中实际跑的 FEP 实现。
  2. **`ZIDATA_` "创建后仍打不开" 的真因**（在 `handle_open_object` 加诊断打印 `obj_type` + 强制按 chunk 再查得到）：第一次 `obj_type=2`(chunk) 在 chunk 创建前打开失败；创建 chunk 后，第二次是 `obj_type=5`(**mutex**) 打开 `ZIDATA_`，`findable_as_chunk=YES` 但作为 mutex 找不到。即 guest 在**和 chunk 同名的独立 mutex 名字空间**里开一个全局 mutex `ZIDATA_`，而这条流程里**没人创建该 mutex**（`mutex_create` 对具名 mutex 已正确设 `global_access`，故不是 `full_name` 可见性 bug，是对象压根没被建）。所以这**不是一个有界的内核可见性 bug**，而是 Zi 引擎内部的对象生命周期期望（mutex 通常由 Zi 服务进程建、其它进程开）在仿真下未被满足；强行补建空对象=喂一个我们不理解、且本就该被绕开的黑盒，方向错。
  3. **结论与正确下一步**：放弃"喂 Zi"（②）；正确方向仍是 ①——但必须先用 ECOM 注册表（`Z:\private\10009D8F\ecom-*.sNN` / 默认 FEP 的 implementation UID，对照 `oom_app::init` 从 `eikpriv.rsc` 读出的 `dll_filename_fep`）**定位默认 FEP 的真实实现 DLL（按 UID 命名的那个）**，再对那个 DLL 名做 `.map`（或在 `oom_app` 设 `default_fep` 时直接改指向 host-bridged 实现 UID `0x101FD65A`）。这是一项需要 ECOM/FEP 注册表分析的独立上游任务，非一行 `.map` 能成。

## 正确版 ① 调查（2026-05-30 续）——定位到默认 FEP，但发现是非确定性 + 二级渲染停滞

- **默认 FEP 身份已确认**：在 `oom_app::init` 加诊断打印从 `eikpriv.rsc` 读出的值，结果是 **`'::101FD65A'`**——即 implementation UID `0x101FD65A`，**正是 host-bridged `CHostBridgedImeFEPPlugin` 在 `ImplementationTable` 里注册的那个 impl**（`avkonfep` patch 复用原生 avkonfep 的 UID2/UID3 = `0x10009D8D`/`0x100056DE`、impl `0x101FD65A`）。所以"正确的 FEP 实现"就是 host-bridged 版，无需另找 DLL。
- **绕过机制其实已在代码里**：`lib_manager` 构造时对 EKA2 设备设 `additional_mode_ = PREFER_PHYSICAL`（libmanager.cpp:1288，注释"Circumvent ROM vs ROFS issue"）；`rom_file_system::open_file`（vfs.cpp:1146-1154）在 ROM 镜像 + 物理文件并存且 `PREFER_PHYSICAL && 大小不同` 时返回**物理**文件。`install_required_rom_patches` 把 host-bridged `avkonfep_general.dll`(6692B) 拷到 `Z:\sys\bin\avkonfep.dll`（原生 176223B 备份到 `.bak`），两者大小不同 → 理论上 ECOM 加载 avkonfep 时应优先拿到 host-bridged 版。
- **真正的症结：非确定性**。同一 build、同一沙盒，反复启动 Calculator：**有时**加载 host-bridged FEP（`ptiengine`/`PtiZiCore` 加载数=0、无 ZIDATA_、无 AV、CPU 空闲 ~1%）；**有时**加载原生 FEP（`PtiZiCore`/`Zi8EnglishUS` 加载、`Can't open object: ZIDATA_` → AV 0x10000 → KERN-EXEC 3）。这就是之前几轮反复"修好了/又崩了"的根源。怀疑方向：①ECOM 究竟按注册名 `avkonfep.dll` 还是按 UID 名 `100056de.dll` 加载该插件（物理替换只盖了前者，loader trace 里 FEP 相关 ECOM 插件是 `10281fc6.dll`/`101fe2aa.dll` 等 UID 名，未见 `100056de.dll`）；②codeseg 缓存——若原生 avkonfep 在某条不带 `PREFER_PHYSICAL` 的路径上被先加载并缓存，后续 ECOM 取到的就是缓存的原生版；③iOS 大小写敏感路径解析对 `avkonfep.dll`/`avkonfep.dll.bak` 并存目录的命中是否稳定。要做确定性修复需沿这三条核实，让 host-bridged 版**始终**被 ECOM 取到（最稳妥可能是在 `oom_app` 设 `default_fep` 时把它指向一个**我们自带、放在可写盘、UID 唯一**的 host-bridged FEP，彻底脱离 ROM 同名/同 UID 的二义性）。
- **二级阻塞：即使 FEP 被绕过，Calculator 仍黑屏**。在"host-bridged 命中、无 Pti/无崩溃"的那次运行里，Calculator 进一步加载 `libOpenVG.dll`（S60v5 Calculator 用 OpenVG 矢量绘制）后**停在 `Create screen device` 之后、未创建 UI 窗口组**（对比 Zip manager 那时已建 window 23/24 并出帧），CPU ~1% 空闲（是阻塞等待，不是 dyncom 慢）。即 FEP 之后还有一层独立的 OpenVG/AVKON UI 起不来的问题。**所以 N97 Calculator 至少要把"FEP 确定性绕过"+"OpenVG/窗口创建停滞"两层都解决**才能渲染；Zip manager 等不吃 FEP、不走 OpenVG 重路径的 app 不受这两层影响，仍是 N97 的推荐验收对象。

## FEP 确定性深挖（2026-05-30 再续）——重定性结论：FEP 其实是稀有副经路，主因是更早的非确定停滞

- 在 `rom_file_system::open_file` 加诊断（命中 `avkonfep`/`100056de`/`fep`/`ptizicore`/`zi8english`/`101fd65a` 任一就打印 path/mode/PREFER/ROM大小/物理大小），跑 ≥6 次：**`avkonfep.dll`/`100056de.dll` 从未被打开**——只看到 `Z:\Sys\Bin\fepbase.dll`（FEP 框架基类，ROM 与物理同为 7764B，大小相同 → PREFER_PHYSICAL 不触发、走 ROM，正常）。说明 **`install_required_rom_patches` 对 avkonfep 的物理文件替换自始至终没被加载过**（FEP 插件根本不经 `z:\sys\bin\avkonfep.dll` 这个名字加载），之前"文件替换让 host-bridged 生效"的判断是错的。
- **真正的分布**：6 次试验里 **5 次根本没加载 FEP 插件**（只到 `fepbase`，然后黑屏、CPU 空闲、不崩）；**1 次**才走到加载原生 Zi（`Zi8EnglishUS`）→ `Can't open ZIDATA_/ZiAutoCh_` → AV 0x10000 → KERN-EXEC。即 **Pti/FEP 崩溃是稀有副经路；绝大多数情况下 Calculator 在更早阶段（FEP 插件实例化之前、OpenVG/窗口创建一带）就非确定地停住**。停滞点逐次不同（有时只到 `fepbase`，有时到 `libOpenVG`，偶尔到 Zi）——典型的 **timing 依赖**（dyncom 下 guest 多线程/服务调度受宿主 wall-clock 影响）。
- **结论修正**：把精力放在"FEP 确定性绕过"是**走偏了**——即使 FEP 100% 绕过，主导的黑屏来自更早的非确定停滞，单解决 FEP 不会让 Calculator 渲染。N97 Calculator 的黑屏本质是 **EKA2L1 在 dyncom 下对 S60v5 这类重 app 启动（AVKON/CONE/OpenVG/多服务握手）的非确定性卡死**，属于体量很大的上游课题，无界、且需要先把 dynarmic 在 sim 稳定（避免 dyncom 的 timing/解码脆弱性）作为前提。**实务建议：N97 用 Zip manager 这类轻量、不吃 FEP/OpenVG 的 app 验收；Calculator 这类重 app 暂不作为 iOS 验收目标，待 dynarmic-on-sim + S60v5 启动稳定性作为独立大任务推进。**
